# 温控逻辑生成、核对与自检 / Thermostat logic document, conformance check & logic review

**模式 A 生成**：产物 `<客户或机型>温控逻辑.md`，1~2 页，只写"怎么动作"。
**模式 B 核对**：产物 `<客户或机型>逻辑核对.md`，客户逻辑 ↔ 实现逻辑逐条判定 + 差异报警。
**模式 C 自检**：产物 `<客户或机型>逻辑审查.md`，不依赖客户需求，对实现本身做逻辑缺陷审查，输出 确认缺陷/需确认 + 后果 + 修复建议。

---

## 范围与证据

- 根据用户目标选择 A（生成）、B（核对）或 C（自检）；用户已指定输入、版本和范围时直接使用，信息不足时才澄清。
- 默认只读模型、代码、参数和需求，仅生成用户要求的产物；修复实现需用户授权。参考示例只演示写法，不能作为当前项目规格或已验证证据。
- 记录实际读取的文件、版本及执行周期；模型与生成代码不一致时分别注明，不能假定已同步。未取得源码、参数或设计依据的结论标为待确认，不填造具体数字。
- 生成文档描述当前可证实的行为，不据此证明实现正确。A 中缺失值就地注明“待确认/To be confirmed”，不受必须给具体数字的排版要求约束。
- 模式 A 读取 [文档模板](references/模板.md)；模式 B 读取 [核对模板](references/核对报告-模板.md)；模式 C 读取 [审查模板](references/逻辑审查-模板.md)。仅在需要格式示例时读取相应示例。

## 模式 A：生成《XX温控逻辑》

按 [文档模板](references/模板.md) 的首次上电、再次开机、转速控制及状态码组织内容；仅描述当前项目存在的功能，不补造未实现功能。篇幅以 1~2 页为目标，完整性优先。

## 写法要求

| 要 | 不要 |
|---|---|
| 一句话一条规则：条件 + 转速/时间 | 不要"分析/溯源/差异/注意事项/待确认"章节 |
| 阈值、时间、转速、步长都给**具体数字** | 不要状态机迁移图、代码行号、变量名堆砌 |
| 统计量写明"累计/每周期清零"、清零时点、运行/停机判定 | 不要只写公式不写统计窗口 |
| 表格只放"输入区间 → 输出"这类映射 | 不要长段落解释、不要建议 |
| 中文在前，英文紧随（可略短） | 不要重复叙述同一规则 |
| 小节内 3~5 行讲完 | 不要超过 4 个 3.x 小节（多了就并） |

## 素材提取

| 来源 | 找什么 |
|---|---|
| `.mdl` Stateflow | `labelString` 里的状态名与 `en:` / `du:` 动作 → 各阶段动作与状态码 |
| `.mdl` 的 Simulink Function | `[条件] {赋值}` 的迁移 → 3.1 / 3.2 / 3.4 的表格 |
| `.mdl` 的 transition | `after(X/T, tick)` → 按实际 tick、取整和起点核算时间；`thermostat_onoff == 1/0` → 启停条件；`state_ctrl.run_mode` → 追查运行状态语义，不直接等同于实际转动 |
| 生成的 `.c`（无模型时） | `/* Entry '状态名' */`、`temporalCounter >= (X / T)`、`xxx_cnt++`、`switch (is_xxx)` |
| 计数器 / 统计量 | `xxx_cnt++`、`xxx_cnt = 0` 所在的状态与分支 → 累加条件、清零时点、统计周期、初始化值 |
| 参数文件 | 转速上下限、时间阈值（模型里写死的数字照抄） |

时间核算：`X/T` 表示理论 tick 数，T 的单位为秒。须核对实际执行周期、数据类型、取整、计数起点、比较边界和调用顺序后计算实际触发时间；不能直接断言 `after(X/T, tick)` 或生成代码阈值恰好为 X 秒。

## 模式 B：客户逻辑 vs 实现逻辑 一致性核对

**输入**
- 客户逻辑：客户给的需求文件 / 邮件 / 表格（如 `逻辑需求.txt`）
- 实现逻辑：模式 A 产出的《XX温控逻辑》，或直接读模型 / 代码

**开始前必须确认 / Input check**

- 模式 B 必须有客户逻辑原件才能开始。用户没提供时，先停下来问，**不要从实现代码反推客户要求，也不要凭印象补**。
- 用户只说"核对一下逻辑"且上下文未提供依据时，先补齐三件事：**客户文件路径/文件名、是否为最新版、核对范围**（全量还是指定条款）。
- 客户逻辑常见存放位置：项目 `文档/`、`0 程序/`、`需求/`、`0_scope/`，或客户邮件附件、图片扫描件（如 `客户机控逻辑.jpg`）。
- 可以在项目目录按关键词（`机控逻辑`、`逻辑需求`、`Control rule`、`需求`、`规格`）搜索候选文件，但**只把候选列给用户确认，不要自行选定**。
- 客户逻辑只有口头版本时，要求用户提供原文或确认过的整理稿，并记录来源与日期。
- 确实找不到客户逻辑时，说明无法执行模式 B，建议改做模式 C 自检；**不要用实现文档冒充客户逻辑**。

**步骤**
0. 先按模式 C 的 C.1 表扫一遍实现内部口径（统计量累计/清零、运行判定、定时器取整）；实现自身前后矛盾时，有证据违反客户要求才记 ❌，证据不足记 ❓，并在差异栏注明"实现内部不一致"。
1. 把客户逻辑**逐条拆成判据**：一条只含一个可检验点（一个数值、一个时间、一个条件或一步顺序）。
2. 在实现里找对应点；找不到对应点也记一条。
3. 按下表给结论。**只比对可检验点，不做主观评价。**

| 结论 | 符号 | 判定 |
|---|---|---|
| 通过 | ✅ | 数值、边界、条件、顺序一致；或有依据证明附加限制不违反任何明确的时间、性能或边界要求 |
| 更严格 | ✅ | 仅在全部约束仍满足时通过；注明附加限制与影响，否则按不符合或待确认处理 |
| 不符合 | ❌ | 数值 / 边界 / 条件 / 顺序不同，或客户要求未实现 |
| 超出要求 | ⚠ | 客户未要求、实现额外增加的规则（提示，不计入不通过） |
| 待确认 | ❓ | 需参数文件或实测才能判定（如转速上下限取值） |

> 同一变量在代码、逻辑文档、测试方案中语义不一致时，不要按其中一份直接判通过；先确认设计意图，再按模式 C 记录内部缺陷。文档可能是直接从有缺陷的代码生成的，会把缺陷写成"规格"。

按 [核对报告模板](references/核对报告-模板.md) 输出；表中分别记录客户条目、需求证据位置、实现证据位置、结论及差异。模式 B 同样以中文在前、英文紧随的方式呈现关键规则与结论。

只有全部判据具备证据且通过、没有待确认项时，才写“全部通过”；存在待确认时列明数量与未核实范围。

**报警写法**
- **结论行放文档最上方**，一眼看出"过 / 不过"。
- "差异与警报"列写**具体差在哪**（数值、边界、顺序），不写"基本一致""大致符合"。
- 用参数就能对齐的差异标"可参数对齐"，否则标"需改逻辑"。
- 客户没写、实现里有的规则一律进 ⚠，不要静默忽略。

## 模式 C：实现逻辑自检

审查对象：生成的 `.c`、`.mdl` Stateflow、参数文件、逻辑文档、测试方案、集成调用点。目标是找**实现自身的逻辑缺陷**，不要求有客户需求。

### C.1 必查项

| # | 类别 | 必查问题 | 典型缺陷 |
|---|---|---|---|
| 1 | 计数器生命周期 | 在哪初始化、累加、清零？清零时点是进入状态、退出状态还是周期边界？多条路径是否都清零？掉电是否保持？ | 停机计数器漏清零，历史停机累计进下一次运行，升档推迟 |
| 2 | 累计 vs 每周期 | 代码、逻辑文档、测试方案对"是否累计"的表述是否一致？代码修复后测试预期是否同步？ | 代码改成每周期清零，文档/测试仍按累计写，测试误判 |
| 3 | 统计口径 | 运行/停机以什么为准（指令、`run_mode`、`observer_wr`）？斜坡、刹车、启动建立、故障停机是否计入？同名统计量在不同分支是否同口径？ | `Ron` 把故障停机算运行，基准每周期 +300 |
| 4 | 状态机退出 | 每个状态的进入/退出条件、超时、异常退出（`run_mode`/故障/输入变化）是否齐全？是否存在无超时等待？ | 等待 `run_mode==0` 的状态无超时，PC/VSP 覆盖时永久等待 |
| 5 | 定时器 | `X/T` 的取整（float/double 截断）、确认窗、计时起点/终点、复位条件；`after(X/T)` 是否真的等于 X 秒？ | 0.5s 写成 9 个 tick（450ms），靠调用顺序才凑成 500ms |
| 6 | 跨模块信号 | 功能路径用的是确认值还是原始值？观察量是否有人消费？调用顺序是否引入延迟？接口方向是否正确？ | 化霜确认值只写观察量，功能仍用原始值 |
| 7 | 故障/异常路径 | 故障时统计量是否把停机算运行？故障恢复是否绕过保护？故障后的基准/计数器是否合理？ | 故障恢复后未重新走 300s 保护 |
| 8 | 文档同步 | 代码修改后，逻辑文档、测试方案、状态码、预期值、模型版本是否同步？ | 文档仍写"`Toff_run` 不随运行周期清零" |

### C.2 证据与输出

- 沿“生命周期 → 统计口径 → 计算与状态后果 → 文档/测试同步”追踪问题，结论包含触发条件及文件位置。
- 存在已确认需求、设计约束或可证明的实现内部矛盾，才标为“确认缺陷”；只有派生文档与代码不同、意图不明或路径未读到时，标为“需确认”。
- 对除零、计数溢出/回绕、饱和、阈值等号、重启与恢复路径检查实际类型和可达输入；不能只看正常启停。
- 按 [逻辑审查模板](references/逻辑审查-模板.md) 输出；需要审查路径示范时再读 [计数器案例](references/示例-逻辑审查-Toff_run_cnt.md)，案例中的阈值、状态名和修复结论均不作为项目默认规则。
- 只给出建议时列明需同步的文档与测试，不勾选“修复已完成”；仅在实际修改且核对后记录已同步。

### C.3 检查

- [ ] 每个相关计数器/统计量均追查初始化、累加、清零、溢出/饱和；未找到的写明
- [ ] 已核对“累计/每周期清零”在现有代码、文档和测试中的描述；缺失资料列为未检查
- [ ] 已核对 `Ron` 与 `Ron_run` 等统计量的口径、统计窗口及差异依据，不强制不同用途使用同一口径
- [ ] 每个等待状态均检查超时及异常退出；设计允许的无限等待不单凭无超时判缺陷
- [ ] 所有 `X/T` 定时器已按 tick 取整核算
- [ ] 确认值/原始值、功能量/观察量没有错位
- [ ] 故障路径没有把停机算运行、没有绕过保护
- [ ] 若已实施修复，核对文档与测试方案同步情况；未实施则列为后续事项

## 检查

模式 A：
- [ ] 结构与骨架完全一致，没有多出章节
- [ ] 可确认的阈值写出数字和单位，缺失值就地标待确认
- [ ] 中英双语，中文在前
- [ ] 状态码表与模型的 `thermostat_state` 赋值一一对应
- [ ] 以 1~2 页为目标，不能为压缩篇幅删掉关键条件

模式 B：
- [ ] 已明确客户逻辑文件（路径/版本/核对范围），上下文已提供的信息不重复询问；缺少需求依据时不判定符合性
- [ ] 客户每条判据都有结论（含"未实现"的条目）
- [ ] 结论行在文档最上方，含不符合项数
- [ ] 每条 ❌ 写明具体差异 + 可否用参数对齐
- [ ] 客户未写但实现里有的规则已列入 ⚠
- [ ] 统计量口径（累计/清零/运行判定）与实现一致

模式 C：
- [ ] 按 C.3 逐项检查，每条缺陷都有触发条件、后果、证据、建议
- [ ] 计数器/统计量已追到初始化、累加、清零三处
- [ ] 已区分修复建议、实际修改和实际验证结果
