## 审查路径

1. **生命周期**：搜 `Toff_run_cnt` 的全部读写点。初始化在 `initialize`；累加在 `start7` 的 else 分支；清零应在进入 `start7` 时。检查正常停机、故障停机、第二次开机三条路径是否都经过入口清零。
2. **口径**：`Ron_run` 的"运行/停机"代码用 `run_mode`；文档用"电机是否在转"；测试用"电机完全停止"。5s 确认窗在代码里算停机，测试方案也写"计入停机"。三处是否同一口径？
3. **后果**：漏清零 → `Toff_run` 偏大 → `Ron_run` 偏小 → 升档推迟/不升档；反之清零过早或漏累加 → 升档提前。若该统计量参与下一周期基准，还会造成基准漂移。
4. **同步**：修复后测试第 8 步的运行中预期从"保持 2800rpm（Ron_run≈42%）"变为"约 23:20 后 3100rpm（Ron_run 80.56%）"；第 4~7、9 步的 `Ron_run` 也要按每周期清零重算。文档 §3.1 的"不随运行周期清零"必须删除。
5. **结论**：代码行为与"每次启停周期独立统计"的设计意图不符 → `确认缺陷`；文档/测试是否同步 → `需确认`，不能因为文档和旧代码一致就判通过。

## 教训

- 文档可能是从有缺陷的代码生成的；"文档 ↔ 代码一致"不等于"逻辑正确"。
- 计数器类缺陷的后果往往不在计数器本身，而在它参与的计算（`Ron_run`、升档阈值、下一周期基准）。
- 代码修复必须同时检查测试方案的预期值，否则测试会把正确行为判为失败。
